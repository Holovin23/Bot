# 10. Сценарии из Telegram-канала → ордера бота (план, без кода)

Дата: 2026-10-13. Статус: решения владельца приняты (раздел 8), часть 1 реализована (раздел 8а).

## 1. Что вы хотите (систематизация)

| # | Требование | Как я его понял |
|---|------------|-----------------|
| 1 | Читать канал | Посты в свободной форме: разборы монет с условными сценариями («если удержим X — идём к Y; если пробьём Z — к W»), посты с результатами прошлых сделок, картинки с линиями поддержки/сопротивления |
| 2 | Извлекать информацию | ИИ превращает пост в структуру: монета, сценарии, условие срабатывания, уровни входа, стопа, целей, срок жизни |
| 3 | «Ячейка» по монете | Для каждой монеты хранится набор активных сценариев. Новый пост: создать ячейку, обновить, отменить или ничего не менять |
| 4 | Отслеживать и торговать | Бот на закрытых свечах проверяет условия сценариев; сработало — ставит ордер со стопом и тейком, заданными сценарием |
| 5 | Сдержанный риск | Короткие стопы, умеренные цели, в среднем R:R ≈ 1:2 |
| 6 | Бэктест поста | Вручную задать пост (текст/картинку) и дату — бот прогоняет сценарий по истории с этой даты |
| 7 | Стоимость | Сколько стоит гонять посты через ИИ постоянно |
| 8 | Без Claude API | Можно ли делать разбор через Claude Code на своём компьютере по подписке |

Посты с результатами прошлых сделок: классифицируем как `RESULTS` и не торгуем по ним (самоотчёт автора — не доказательство, его проверит наш бэктест).

## 2. Насколько это реалистично — честно

**Технически реалистично, большая часть фундамента уже есть.** Вопрос «заработает ли» — не технический, а в том, есть ли у автора канала преимущество. Это и должен показать бэктест по архиву до paper/demo.

Что хорошо получится:
- Извлечь из текста монету, направление, числа уровней и условие — Claude делает это надёжно, если схема жёсткая.
- Сделать сценарий обычной стратегией: тогда бэктест, paper, демо и риск-менеджер работают с ним без изменений (правило CLAUDE.md «один код для всех режимов»).

Где реальные трудности:
1. **Уровни с картинок неточные.** Модель читает график по оси цен с ошибкой порядка 0,3–1%. Для стопа в 0,5–1 ATR это много. Решение: числа из текста важнее картинки; уровни «с картинки» помечаются как приблизительные и уточняются кодом (ближайший экстремум свечей в окне ±1%); стоп по уровню только с картинки — только после вашей проверки в интерфейсе или не торгуется.
2. **Сценарии расплывчатые.** «Если удержим поддержку» — что значит «удержим»? Нужен небольшой словарь триггеров (раздел 4.2). Всё, что в него не укладывается, — ячейка в статусе «не торгуется, только показ».
3. **Мало сделок.** При 1–2 постах в день и срабатывании части сценариев — десятки сделок в год. Статистика будет слабой (как у EXP-003: t ≈ 1). Решение: сравнение со случайными входами тех же направления и R:R (как в `research/baseline.py`), не делать выводы по 20 сделкам.
4. **Заглядывание в будущее при бэктесте архива.** Модель могла «видеть» историю цен при обучении. Защита: модель только извлекает то, что написано (каждое число подкрепляется цитатой из поста — проверка кодом), вход только после `published_at`, и сверка с ручной разметкой (`llm_parser --label` уже есть).
5. **R:R 1:2 с короткими стопами.** Нужна доля прибыльных сделок > ~36–40% с учётом комиссий; слишком короткий стоп выбивается шумом. Существующие проверки риск-менеджера (стоп не ближе 0,5 ATR, издержки < 20% цели) это отсекут — так и должно быть.
6. **Принцип архитектуры.** Сейчас правило: «LLM только извлекает информацию, не создаёт сделки и не меняет стопы». В этом плане LLM по-прежнему **только извлекает сценарий автора**, а решение о сделке, объём и проверки делает детерминированный код и риск-менеджер. Но уровни стопа и цели будут из поста — это ослабление правила, нужно ваше явное решение (раздел 8, п. 1).

Вывод: **реалистично как исследование и paper-бот за несколько недель работы**; на демо — только если архив покажет преимущество над случайными входами.

## 4. Общее ядро (одинаково для обоих планов)

### 4.1 Поток данных

```
Telegram-пост (текст + картинки)
   → разбор ИИ (API или Claude Code) → JSON по схеме v2
   → проверка кодом (схема, цитаты, уровни с правильной стороны, монета есть на Bybit)
   → применение к ячейкам монеты: CREATE / UPDATE / CANCEL / IGNORE (+ история версий)
   → стратегия telegram_scenario на закрытых свечах: условие сработало?
   → Signal (вход, стоп, цель, signal_id из id сценария)
   → риск-менеджер (те же проверки, R:R ≥ 2) → Broker (paper / demo)
```

### 4.2 Ячейка сценария (SQLite, таблица `scenarios` + `scenario_history`)

| Поле | Пример | Примечание |
|------|--------|-----------|
| `scenario_id` | `tg-SOLUSDT-20261013-1` | основа для `signal_id`/`orderLinkId` |
| `symbol` | `SOLUSDT` | |
| `side` | `LONG` | |
| `trigger` | `close_above 152.0 на 1h` | словарь: `close_above`, `close_below`, `retest_from_above` (пробой, затем касание и закрытие выше), `retest_from_below`, `touch_zone` (касание зоны и закрытие в нужную сторону) |
| `trigger_timeframe` | `1h` | по умолчанию из конфига (15m или 1h) |
| `stop` | `147.5` | уровень отмены сценария автора; если автор не назвал — сценарий не торгуется |
| `targets` | `[158, 165]` | берётся первая цель с R:R ≥ 2 от фактического входа; нет такой — сделка отклоняется |
| `valid_until` | `+72 ч` | если автор не указал — значение по умолчанию из конфига |
| `level_source` | `text` / `image` | уровни только с картинки → «приблизительно», нужна проверка |
| `quotes` | «если закрепимся над 152…» | дословные цитаты; код проверяет, что они есть в посте |
| `status` | `ACTIVE` → `TRIGGERED` / `EXPIRED` / `CANCELLED` / `INVALIDATED` | `INVALIDATED`: цена прошла стоп до входа |
| `post_ids`, `created_at`, `updated_at` | | ячейка видна стратегии только после `created_at` (без заглядывания вперёд) |

Правила обновления (чистые функции, с тестами):
- Новый пост меняет только ячейки в `ACTIVE`. Открытую позицию пост не трогает — у неё свой стоп и тейк на бирже (правило «LLM не меняет стопы» соблюдено).
- Модель получает активные ячейки монеты и для каждой отвечает `KEEP / UPDATE / CANCEL`, плюс список новых. Код применяет, старая версия уходит в историю.
- Пост `RESULTS` или пост без торгуемых условий → `IGNORE`.

### 4.3 Стратегия `telegram_scenario`

Обычная стратегия по API `strategies/base.py`: получает снимок ячеек «как они были на момент свечи», на закрытии свечи проверяет триггер, создаёт `Signal` (вход — открытие следующей свечи). Тест `find_lookahead` обязателен.

### 4.4 Бэктест одного поста (ваш п. 6)

```
uv run python -m bot.research.scenario_backtest --post post.txt --image chart.png \
    --date "2025-03-01 10:00"
```
- Разбирает пост (или берёт готовый JSON: `--scenario scenario.json` — без ИИ и без затрат),
- показывает извлечённые сценарии,
- прогоняет их по 1m-истории с этой даты через обычный движок (комиссии, проскальзывание, funding),
- отчёт: сработал ли триггер, когда, итог в R, график с уровнями. Та же кнопка во вкладке «Сценарии».

### 4.5 Бэктест всего архива (решает, есть ли смысл)

Выгрузить архив канала → разобрать все посты → прогнать все сценарии → сравнить с 1000 случайными входами того же направления, стопа в ATR и R:R → запись в `research/trials.json` (DSR). Порог перехода к paper: преимущество над случайными входами и ≥ 30 сделок.

## 6. План B: без API, через Claude Code на вашем компьютере

То же ядро (A1, A2, A4–A9 без изменений), меняется только «кто разбирает пост»: вместо вызова API — скилл Claude Code.

Как это устроено:
1. В репозитории скилл `.claude/skills/telegram-scenarios/SKILL.md`: инструкция «возьми неразобранные посты, посмотри картинки, заполни JSON по схеме v2, сохрани через команду импорта».
2. Команды бота, которые скилл вызывает:
   - `uv run python -m bot.scenarios pending` — неразобранные посты с путями к картинкам и активными ячейками монет;
   - `uv run python -m bot.scenarios import file.json --post <id>` — проверка схемы и цитат, применение к ячейкам. Тот же код, что в плане A, поэтому ошибки модели ловятся одинаково.
3. Запуск:
   - вручную: в Claude Code набрать `/telegram-scenarios` после нового поста;
   - по расписанию: Планировщик заданий Windows раз в 15–30 минут запускает `claude -p "/telegram-scenarios"` с разрешёнными только этими командами.

Ограничения плана B (честно):
- **Компьютер должен быть включён и не спать**, Claude Code вошёл в аккаунт. Это не сервер.
- **Задержка** от поста до ячейки — до интервала расписания; для сценариев на 1h это терпимо.
- **Лимиты подписки общие** с вашей обычной работой в Claude Code; если лимит исчерпан, посты ждут.
- **Правила использования.** Подписка рассчитана на личную работу человека с Claude Code. Ручной запуск скилла — это обычное использование. Автоматический запуск по расписанию для личной автоматизации технически работает, но я не могу гарантировать, что это соответствует действующим условиям: перед тем как полагаться на это, прочитайте актуальные условия подписки. Для работы 24/7 правильный путь — API-ключ.
- **Разбор должен быть одинаковым в бэктесте и в работе.** Если архив разбирался одним способом (например, API), а живые посты другим (Claude Code), результаты бэктеста переносятся хуже. Лучше один способ на всё, или проверить совпадение на 30–50 постах.

Где план B особенно хорош: разовый разбор архива канала и ручная разметка — это интерактивная работа, и подписка тут подходит естественно.

## 7. Стоимость Claude API (оценка)

Это **оценка**, не замер. Цены Claude API на 2026-10 (за 1 млн токенов, вход / выход): Opus 5.5 — $4 / $20, Sonnet 5.5 — $2 / $10, Haiku 5.5 — $0,10 / $0,50. Batch API — скидка 50% (подходит для архива, не для живых постов).

Допущения на один пост: системный промпт и схема ~2 тыс. токенов, текст поста ~0,8 тыс., одна картинка ~1,6 тыс., активные ячейки монеты ~1 тыс. → **~5–6 тыс. токенов входа**; ответ с рассуждением ~1,5–2,5 тыс. токенов выхода.

| Модель | Один пост | 3 поста/день, месяц | 10 постов/день, месяц | Архив 1000 постов (Batch) |
|--------|-----------|---------------------|-----------------------|---------------------------|
| Opus 5.5 | ~$0,05–0,07 | ~$5–6 | ~$15–20 | ~$25–35 |
| Sonnet 5.5 | ~$0,02–0,04 | ~$2–3 | ~$7–10 | ~$12–18 |
| Haiku 5.5 | < $0,002 | < $0,2 | < $0,5 | ~$1 |

Кэширование системного промпта уменьшит вход ещё примерно на треть. Итог: **при 1–5 постах в день — единицы долларов в месяц**. Модель выбираем по сверке с вашей ручной разметкой: если Sonnet или Haiku совпадают с ней так же, как Opus, берём дешевле. Точную цифру даст первый прогон: в `post_parses` стоит сохранять `usage` (токены) каждого вызова.

## 8. Решения владельца (2026-10-13)

1. **Стоп и цель от автора разрешены.** Автор называет их редко, поэтому есть значения по
   умолчанию (`scenarios/levels.py`, параметры стратегии):
   - стоп — за уровнем входа на 0,5 ATR (для зоны — за её дальним краем), для входа «сейчас» — 1,5 ATR от входа;
   - цель — первая цель автора с R:R ≥ 2; если цели автора есть, но все ближе 2R — сделки нет;
     если целей нет — вход ± 2R;
   - дальше обычные проверки риск-менеджера: стоп 0,5–4 ATR, издержки < 20% цели, R:R ≥ 2.
2. **Делаем оба плана**: Б (Claude Code) — чтобы попробовать, А (Claude API) — если подойдёт.
   Код общий, отличается только «кто разбирает пост».
3. **Белый список монет**: `scenarios.symbols` в `config/default.yaml` (пока BTCUSDT, ETHUSDT —
   впишите нужные монеты; для торговли монета нужна и в instruments).
4. **Срок жизни сценария не ограничен.** Ячейка живёт, пока её не отменит новый пост, пока
   цена не дойдёт до стопа автора до входа (сценарий сломан) или до его первой цели
   (движение упущено). Параметр `max_age_days` включает ограничение, по умолчанию 0 — без него.
5. **Канал**: t.me/Prizrak_trade. **Скриншоты с профитом или убытком не анализируются**:
   каждая картинка классифицируется (график / скриншот P&L / другое), уровни берутся
   только с графиков, посты с итогами сделок (`RESULTS`) ячейки не меняют.
